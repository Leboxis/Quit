# V2.1 · Fiabilité

Objectif : valider l'usage réel de Quit sur les installations visées, avec conservation des données et commandes accessibles. Cette étape prolonge V2 ; le journal, les plans et les statistiques existent déjà. V3 à V10 restent hors de ce lot, notamment le blocage Screen Time.

## État au 6 octobre 2026

Corrections et couverture de test préparées dans le dépôt. **V2.1 n'est pas encore validée sur iPhone.** Les tests Python et la revue visuelle Figma ont été exécutés sur Windows ; la compilation Swift, XCTest et les essais d'installation demandent encore une exécution native.

[Figma V2.1 · Fiabilité](https://www.figma.com/design/5wrVQf5TcnIVAJmnLN8ePs?node-id=23-261) contient six états éditables : SOS standard, SOS avec grands caractères, retour au SOS, sauvegarde inaccessible, verrouillage indisponible et notifications refusées. Les composants et variables existants sont réutilisés. Inter reste la police de prévisualisation Figma ; l'app utilise SF Pro système. Les tailles agrandies illustrent le reflow et ne reproduisent pas exactement les métriques AX5. Les maquettes ne prouvent pas le fonctionnement d'une installation.

## Changements de ce lot

- Lecture et création des IPA avec des chemins ZIP POSIX sur tous les systèmes. Le défaut initial provoquait deux erreurs de tests sur Windows. Les noms de chemins dangereux et les chemins d'exécutable invalides sont refusés explicitement.
- Émotions sur une colonne aux tailles d'accessibilité, largeur minimale proportionnelle à la police aux autres tailles, libellés et boutons capables de grandir verticalement.
- Choix en menus natifs aux tailles d'accessibilité dans l'onboarding, le check-in, le SOS et les réglages d'apparence ; contrôles segmentés conservés aux tailles standard.
- Intensité et commandes du journal disposées verticalement aux tailles d'accessibilité. L'affichage du temps SOS devient un texte avec une progression, sans cadran de hauteur fixe.
- Temps SOS recalculé à la réactivation de l'app à partir de son échéance, sans attendre la prochaine seconde de rafraîchissement.
- Demande de déverrouillage identifiée et annulée au passage en arrière-plan : une réponse tardive est ignorée, y compris si une nouvelle tentative a commencé. Une authentification terminée pendant l'inactivité du dialogue système attend le retour actif ; un passage en arrière-plan annule aussi cette attente.
- Changement du verrouillage annulé si les réglages passent en arrière-plan ou se ferment. Les autres modifications et la fermeture des réglages sont temporairement désactivées pendant une demande de permission.
- État du rappel relu à l'ouverture des réglages et au retour actif : refus iOS, autorisation à demander, horaire absent, rappel programmé ou alertes discrètes. L'horaire est vérifié dans les demandes réellement en attente, sans demander de permission ni réactiver automatiquement le rappel. Les confirmations parlent de programmation, sans garantir la réception.
- Onze tests XCTest supplémentaires couvrent les réponses d'authentification obsolètes, la reprise après le dialogue système, les refus/révocations et l'identité, la répétition et l'horaire des notifications. Ils sont écrits mais **non exécutés sur cet hôte Windows**.
- Tests de persistance couvrant tous les types d'enregistrements, les identifiants, les préférences, l'échec d'écriture et les permissions lors d'un import.
- Tests UI isolés dans un répertoire dédié par test, conservé lors des relancements de ce test. Le choix de ce répertoire et la taille AX5 forcée sont réservés à la configuration Debug ; la build Release conserve le stockage habituel et les réglages système.
- Recette UI standard et AX5 sur deux modèles distincts, compact et Max/Plus, dans un workflow natif séparé, nocturne ou manuel. Les deux modèles s'exécutent en parallèle, chaque job étant limité à cinq minutes. Le modèle compact est choisi dans le runtime le plus récent disponible : ce n'est pas nécessairement un petit iPhone de 375 pt. Une recette physique sur petit écran reste requise. Un modèle absent fait échouer la sélection au lieu de réduire silencieusement la couverture.

Le bundle `fr.leboxis.quit`, le fichier `quit-v1.json`, le schéma 1 et les données V1/V2 sont conservés. Pas de nouvelle permission ni d'extension.

Le test AX5 traverse l'onboarding, choisit une émotion dans le check-in, utilise les commandes fixes du SOS, passe en arrière-plan, vérifie que le temps restant a diminué, enregistre la session et relance l'app sans repasser par l'onboarding. Il ne valide pas à lui seul l'absence de troncature dans tous les écrans : les captures et une revue des autres vues sont nécessaires.

### Budget GitHub Actions

Le workflow courant lance les contrôles Python et la build en parallèle. Ses limites sont d'une minute pour les contrôles, quatre minutes pour la build et une minute pour la publication, soit un budget de cinq minutes sur le chemin build/publication, hors file d'attente et délai d'annulation GitHub. Il ne compile plus le simulateur. Homebrew ne se met pas à jour pendant le run, XcodeGen n'est installé que s'il manque, et l'IPA déjà compressé est transféré sans recompression.

Le workflow natif compile uniquement le simulateur, sans deuxième compilation appareil ni publication. Chaque modèle dispose de cinq minutes ; les deux jobs sont indépendants et parallèles. Les relances automatiques des tests après un problème d'accessibilité du simulateur sont retirées pour respecter ce budget. Un dépassement est un échec, jamais une validation. Les temps de réussite à froid et à chaud restent à mesurer sur GitHub.

Les tests Python et la vérification de l'IPA bloquent toujours la publication. Les tests XCTest/UI sont déplacés hors du chemin de publication à la demande de l'utilisateur ; ils restent nécessaires à la recette V2.1. Les anciens runs encore actifs sont annulés lorsqu'un nouveau run arrive pour la même référence.

## Recette sur appareils

Pour chaque ligne, consigner : modèle d'iPhone, version iOS, version/build Quit avant et après, version de SideStore ou LiveContainer, mode d'installation/signature/conteneur, résultat, date et preuve. Les mentions « À tester » ne sont pas des succès.

Préparer dans la version actuellement installée une intention, un check-in incertain, une session SOS, un épisode, un plan, deux exercices terminés, une réflexion et des préférences non standard. Exporter une sauvegarde dans un emplacement privé pour la comparaison avant/après.

| Cas | Manipulation | Critère d'acceptation | État |
| --- | --- | --- | --- |
| Installation SideStore | Installer l'IPA par la méthode habituelle ; terminer l'onboarding et relancer | App utilisable, saisies conservées | À tester |
| Mise à jour SideStore | Mettre à jour la même installation via la source, sans désinstaller | Aucune remise à zéro ; valeurs et UUID inchangés dans les exports avant/après | À tester |
| Installation LiveContainer | Importer/préparer l'IPA avec le mode choisi ; terminer l'onboarding et relancer | Parcours de base utilisable, même si une permission n'est pas disponible | À tester |
| Mise à jour LiveContainer | Mettre à jour l'app dans le même conteneur/mode | Intention, journal, plans, leçons, réflexions et préférences conservés | À tester |
| Petit et grand écran | Revoir onboarding, Aujourd'hui, check-in, SOS, épisode, journal, parcours, statistiques, aide et réglages en portrait et paysage | Aucun texte essentiel illisible ; chaque commande accessible par défilement ; barres fixes utilisables | À tester |
| Grandes polices | Taille standard, XXXL et AX5 dans Réglages iOS, sur les deux tailles d'écran ; clair et sombre | Libellés lisibles, choix accessibles, aucun chevauchement ; commandes SOS/check-in accessibles | À tester |

| Confidentialité | Ouvrir le sélecteur d'apps, verrouiller l'appareil puis revenir ; refaire pendant l'authentification, depuis le SOS et depuis les réglages | Cache de confidentialité visible à l'inactivité, y compris pour les vues présentées ; nouveau déverrouillage requis au retour ; aucune réponse tardive ne donne accès | À tester |
| Modifier le verrouillage puis quitter | Pendant la demande Face ID des réglages, passer en arrière-plan puis revenir et retenter | Préférence inchangée après annulation ; commandes de nouveau utilisables ; ancienne réponse ignorée | À tester |
| Notifications autorisées | Choisir un horaire proche, autoriser puis mettre l'app en arrière-plan | Rappel discret reçu à l'horaire choisi si l'installation le permet | À tester |
| Notifications refusées / révoquées | Refuser ; puis révoquer dans iOS après une autorisation et revenir aux réglages Quit sans retenter | Refus affiché dès le retour ; accès aux réglages iOS ; aucune fonction du parcours bloquée ; aucune affirmation erronée d'activation | À tester |
| Rappel absent / alertes discrètes | Sur une installation de test, retirer la demande en attente ; tester aussi avec alertes iOS désactivées | Horaire absent signalé ; alertes discrètes expliquées ; aucune réactivation automatique | À tester |
| Actualiser / désactiver un rappel | Changer l'heure puis désactiver avant échéance | Pas de doublon ; aucun ancien rappel reçu après désactivation | À tester |
| SOS en arrière-plan | Pendant l'observation, quitter quelques secondes, puis plus longtemps que la durée ; répéter au choix d'action | Temps recalculé immédiatement au retour, jamais négatif ; choix conservé dans la session vivante ; une seule session sauvegardée | À tester |
| Export / import | Exporter, importer après confirmation et relancer | Toutes les données restaurées ; verrouillage de cet appareil conservé ; rappel à réactiver volontairement | À tester |
| Sauvegarde inaccessible | Sur une copie de test, rendre le fichier illisible et lancer l'app | Erreur et actions de récupération visibles ; fichier non remplacé avant action explicite | À tester |

Un changement de conteneur ou une désinstallation peut supprimer le stockage de l'installation : tester ce scénario séparément avec export/import volontaire. Une session SOS interrompue par la fermeture forcée du processus n'est pas restaurée par ce lot ; la reprise durable relève de V4.

## Sortie de V2.1

V2.1 peut être déclarée validée après une compilation et des tests natifs réussis, la recette documentée sur SideStore **et** LiveContainer, et la correction des anomalies bloquant la conservation des données, la confidentialité ou une commande essentielle. Une capacité indisponible dans un mode d'installation peut être acceptée si elle est clairement indiquée et si le parcours de base reste utilisable.

La numérotation automatique des builds reste `0.2.<run_number>` ; V2.1 désigne ce lot produit, sans modifier le contrat de version utilisé par le catalogue. Le push sur `main` déclenche la compilation et, si les contrôles réussissent, la publication automatique d'une build ; cette publication ne vaut pas validation de la recette V2.1.
